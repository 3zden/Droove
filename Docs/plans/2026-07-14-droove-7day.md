**Goal:** A running ride-hailing platform (6 Spring Boot services, 2 FastAPI services, web + mobile frontends, Kafka + Redis + Postgres, one real ECS deploy) that the user can defend line-by-line in a backend/infra interview.

## §Contracts (single source of truth — every task conforms to this section)

### Trip state machine (trip-service owns it)

```
REQUESTED ──► MATCHED ──► DRIVER_ARRIVED ──► IN_PROGRESS ──► COMPLETED
    │             │              │
    ▼             ▼              ▼
 CANCELLED    CANCELLED      CANCELLED
    │
    ▼ (matching exhausts 3 rounds)
 NO_DRIVERS_FOUND
```

Legal transitions map (enforced in one place, `TripStateMachine.java`):

| From | To |
|---|---|
| REQUESTED | MATCHED, CANCELLED, NO_DRIVERS_FOUND |
| MATCHED | DRIVER_ARRIVED, CANCELLED |
| DRIVER_ARRIVED | IN_PROGRESS, CANCELLED |
| IN_PROGRESS | COMPLETED |

### Kafka topics & event envelope

| Topic | Partitions | Key | Producers → Consumers |
|---|---|---|---|
| `trip-events` | 6 | tripId | trip-service → notification-service, payment-service, analytics-sink |
| `match-requests` | 3 | tripId | trip-service, scheduling-service → matching-service |
| `notifications` | 6 | targetUserId | matching-service → notification-service |

Envelope on `trip-events` (verbatim schema, Java record `TripEvent` and Pydantic model `TripEvent` must match):

```json
{
  "v": 1,
  "eventId": "7f9c...uuid",
  "eventType": "TRIP_REQUESTED|TRIP_MATCHED|DRIVER_ARRIVED|TRIP_STARTED|TRIP_COMPLETED|TRIP_CANCELLED|NO_DRIVERS_FOUND",
  "tripId": "uuid",
  "riderId": "uuid",
  "driverId": "uuid-or-null",
  "occurredAt": "2026-07-15T18:04:05Z",
  "payload": { "fareCents": 2350, "surge": 1.2 }
}
```

`match-requests` message: `{"v":1,"tripId":"uuid","riderId":"uuid","pickupLat":33.5731,"pickupLng":-7.5898,"fareCents":2350}`
`notifications` message: `{"v":1,"targetUserId":"uuid","type":"DRIVER_OFFER|TRIP_UPDATE","payload":{...},"occurredAt":"..."}`

Payment consumption mapping (payment-service consumer group `payment-service`):
- `TRIP_MATCHED` → `ESCROW_HOLD` (rider wallet → escrow, `fareCents`)
- `TRIP_COMPLETED` → `DISBURSE` (escrow → driver 80%, escrow → platform 20%; odd cent goes to platform)
- `TRIP_CANCELLED` → `REFUND` (escrow → rider wallet, only if a hold exists for the trip)
- Idempotency key for every ledger transaction = `eventId`.

### Redis keys

| Key | Type | Owner writes | Purpose |
|---|---|---|---|
| `drivers:geo` | GEO (member=driverId) | location-gateway (M1) | nearest-driver index |
| `driver:{id}:status` | STRING `AVAILABLE\|BUSY\|OFFLINE`, TTL 15s | location-gateway sets AVAILABLE on connect + `EXPIRE`-only refresh per ping; matching CAS→BUSY; disconnect → DEL + ZREM | liveness = TTL heartbeat |
| `driver:pos:{id}` | pub/sub channel | location-gateway publishes each ping | rider live tracking |
| `schedule:bookings` | ZSET score=epochSec(pickup−10min), member=bookingId | scheduling-service (M3) | future-booking trigger queue |
| `offers:expiry` | ZSET score=epochSec(expiry), member=offerId | matching-service | offer timeout sweep (same pattern as M3) |
| `offer:{offerId}` | HASH {tripId,driverId,fareCents}, TTL 30s | matching-service | live offer state |
| `surge:{geohash5}` | INT counter, TTL 300s | trip-service INCRs on request | pricing surge input |
| gateway rate-limit keys | (managed by SCG RequestRateLimiter) | gateway (M5) | per-user throttle |

### WebSocket protocols (FastAPI side)

- `WS /ws/location?token=JWT` — role DRIVER. Client → server every ~2s: `{"lat":33.57,"lng":-7.59,"heading":90,"ts":"..."}`. Server behavior = M1.
- `WS /ws/track/{driverId}?token=JWT` — role RIDER. Server → client: relayed position JSON from `driver:pos:{driverId}` pub/sub.
- `WS /ws/notifications?token=JWT` — any role. Server → client: `{"type":"DRIVER_OFFER"|"TRIP_UPDATE","payload":{...},"ts":"..."}` routed by userId from the two Kafka topics.

### Matching algorithm (matching-service; geo query is M1, orchestration is CLAUDE scaffold + M6)

On `match-requests` message: up to 3 rounds → `findNearest(pickup, radiusKm=5, limit=5)` excluding already-offered drivers → take nearest AVAILABLE → CAS status AVAILABLE→BUSY (Lua, provided) → write `offer:{id}` hash + `offers:expiry` ZSET (+15s) → publish `DRIVER_OFFER` notification. Accept → `PATCH /trips/{id}/assign` → done. Decline/timeout (expiry sweeper, 1s poll) → CAS driver back to AVAILABLE → next candidate. Rounds exhausted → call trip-service internal `POST /trips/{id}/no-drivers` (→NO_DRIVERS_FOUND).

CAS Lua (provided in scaffold, `matching-service/src/main/resources/cas.lua`):

```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
  redis.call('SET', KEYS[1], ARGV[2], 'KEEPTTL')
  return 1
end
return 0
```

### Ledger model (payment-service; M4)

```
accounts(id UUID PK, type RIDER_WALLET|DRIVER_WALLET|ESCROW|PLATFORM_REVENUE|EXTERNAL,
         owner_id UUID NULL, trip_id UUID NULL,        -- ESCROW rows: one per trip
         cached_balance_cents BIGINT NOT NULL DEFAULT 0)
ledger_transactions(id UUID PK, type ESCROW_HOLD|DISBURSE|REFUND|TOPUP,
         idempotency_key VARCHAR UNIQUE NOT NULL, trip_id UUID NULL, created_at)
ledger_entries(id UUID PK, tx_id FK, account_id FK, amount_cents BIGINT NOT NULL, created_at)
```

Invariants (each is a RED test in T21): (1) per-transaction `SUM(amount_cents) = 0`; (2) entries are append-only (`@Immutable`, no update/delete paths; prod note: `REVOKE UPDATE` — documented, not built); (3) replaying the same `idempotencyKey` returns the original tx, writes nothing; (4) concurrent posts against one account serialize via `SELECT … FOR UPDATE` with accounts locked in sorted-UUID order (deadlock avoidance); (5) wallet/escrow accounts may not go negative (EXTERNAL may — it's the money-in source).

### Fare formula (pricing-service, CLAUDE-owned)

`fare = max(700, round((500 + 120*distanceKm + 30*durationMin) * surge))` cents; `durationMin = distanceKm/30*60` (assumed 30 km/h); `distanceKm` = haversine; `surge = clamp(1.0 + 0.2*floor(cellCount/5), 1.0, 3.0)` where `cellCount = GET surge:{geohash5(pickup)} or 0`.

**Interfaces — Produces (M4 implements):**

```java
/** Append-only, atomic, idempotent. entries must sum to 0; accounts locked in
 *  sorted-UUID order; non-EXTERNAL accounts may not go negative; replay of
 *  idempotencyKey returns the original transaction unchanged. */
LedgerTransaction postTransaction(String idempotencyKey, TxType type,
                                  UUID tripId, List<EntryCmd> entries);
void onTripMatched(TripEvent e);    // ESCROW_HOLD  rider→escrow(trip), fareCents
void onTripCompleted(TripEvent e);  // DISBURSE     escrow→driver 80% + escrow→platform 20% (odd cent→platform)
void onTripCancelled(TripEvent e);  // REFUND       escrow→rider, only if hold exists (else no-op)
record EntryCmd(UUID accountId, long amountCents) {}
```

RED tests (the invariants of §Contracts, each one is an interview answer):
1. entries summing ≠ 0 → `UnbalancedTransaction`, nothing persisted;
2. balanced post → entries written, cached balances updated, `SUM(entries per account) == cached_balance` (checked by raw SQL);
3. same idempotencyKey twice (sequential) → second returns first's txId, entry count unchanged;
4. **race:** two threads, same idempotencyKey, `CyclicBarrier` start → exactly one tx row (unique constraint is the backstop — test proves the handler converts the violation into "fetch and return original");
5. **race:** ESCROW_HOLD and DISBURSE on the same escrow concurrently → both succeed serially or one fails cleanly — final balances consistent, no negative escrow;
6. insufficient rider balance → `InsufficientFunds`, no partial writes;
7. Hibernate flush of a modified `LedgerEntry` → no UPDATE issued (`@Immutable` proof);
8. full replay: MATCHED,COMPLETED consumed twice each (redelivery sim) → driver got exactly 80% once; 2350¢ splits 1880/470.
